Today's session focuses on the three middle stages.

First, let's follow a request through the server. The tokenizer splits your prompt into pieces called tokens and gives each an ID. The model turns those IDs into lists of numbers it can calculate with.

[click] Then comes prefill. The model processes the prompt in parallel.

[click] It stores keys and values for each token in each attention layer. This KV cache is the request's working memory, so later tokens can look back without reprocessing the prompt.

[click] Now decode reads the weights, the numbers learned during training, and that cache to generate each new token.

[click] Stream sends those tokens back to the user as they arrive. First-token wait and next-token wait are different problems.

Movement 1 · the asymmetry

Long-prompt prefill is usually compute-bound. Small-batch decode is usually memory-bound.

Prefill

n tokens in one pass. Matrix units (tensor cores) saturated. Cost scales with FLOPs (math operations).

Decode

weights from memory

1 token per pass. Cores wait on memory. Cost scales with bytes.

Schematic.

Those two phases make different demands on the same chip. A long prefill has lots of tokens to work on together, keeping the matrix units busy. We usually hit the compute limit.

[click] A single conversation has to wait: token ten needs token nine. Decode does a little math, then waits for bytes from memory. That's our starting point. A large batch, with many conversations processed together, can push decode toward compute; a short prefill can hit the memory limit.

We've estimated a ceiling. Now let's compare it with what the server actually does. At short context, divide one-user tokens per second by that ceiling. That's model bandwidth utilization, or MBU.

[click] If it's low, look for overhead: GPU operations, their launch costs and batch shape. Profile a test server with Nsight Systems or PyTorch; never enable profiling in production.

[click] If the weights dominate, shrink the weights.

[click] If the context dominates, shrink the KV cache.

[click] And if we can predict the next few tokens cheaply, get more tokens from each weight read. Let's start with work we don't need to repeat.

Greedy illustration; sampled decoding preserves the target distribution in theory; finite-precision numerics can differ (vLLM v0.31.0 lossless guarantees). Leviathan et al., arXiv:2211.17192: 2×–3× on T5-XXL, batch 1.

So far we've saved work or reduced bytes. Speculative decoding tries to get several tokens from each expensive weight read.

[click] First, a drafter guesses a few tokens ahead. That's a cheaper predictor, such as a smaller model or extra prediction layers attached to the main model.

[click] The main model, called the target, checks those guesses in one pass. With few conversations running, it often has spare compute while waiting for memory. We use that compute to check several tokens together.

[click] This example uses greedy decoding: always pick the most likely token. Keep the matches, then correct the first miss. Here we get four tokens for one weight read. [pause 3s: follow the accepted tokens] Sampling instead needs probability checks and corrected resampling to preserve the target distribution in theory. Hardware rounding can still change outputs.

[click] Then a small scorer picks the entries main attention reads: one thousand twenty-four on V4-Pro, five hundred twelve on Flash. The indexer still does its own reads.

[click] HCA, heavily compressed attention: the other half squeeze a hundred twenty-eight tokens into one, and read them all: a coarse map of the whole document.

[click] And the last hundred twenty-eight tokens stay uncompressed, because a token can't attend to its own unfinished block.

[click] Compare the growing cache bytes per token: about sixty-six thousand for Qwen three point eight, forty-eight thousand for V3.2, and five thousand for V4. V4.1 Flash uses CSA two: layers share entries and picks, and the cache uses four bits. Eight hundred ninety bytes, about seventy-four times less than the Qwen example. These are different architectures and precisions; the fixed window and state are extra.

Keep the first token wide. At 2-bit nonuniform, without sparse outliers: perplexity 23.3 without it, 9.6 with it. 16-bit: 4.6.

KIVI, arXiv:2402.02750 · KVQuant, arXiv:2401.18079, Table 13 (Llama-2-13B, Wikitext-2): with 1% sparse outliers, keeping the first token wide changes perplexity from about 4.85 to 4.78. Heatmaps are schematic.

Large values show up in different places in keys and values. In these measurements, large key values line up by channel: the same position across tokens.

[click] That makes a separate quantization scale per key channel useful.

[click] Large value entries don't line up the same way, so values use a scale per token.

[click] The first token can attract disproportionate attention, an attention sink. In this two-bit nonuniform test, rare large values weren't stored separately. Keeping just the first token wide takes perplexity from twenty-three to under ten, still above the sixteen-bit baseline of four point six. If KV quantization hurts quality, investigate scale grouping, outlier handling and the first token.

Schematic. All-reduce exchanges and sums each GPU's partial results.

What if one model needs several GPUs? Tensor parallelism splits each layer across them. After every layer, an all-reduce exchanges and sums their partial results. That makes the GPU interconnect another bandwidth limit. Prefer fast links such as NVLink; keeping tensor parallelism inside a node is a useful starting rule.

[click] Pipeline parallelism gives each GPU a range of layers. Intermediate results hop between stages, so there's much less communication and ordinary networks become more practical. Start with tensor parallelism inside a node and pipeline parallelism across nodes, then measure your topology.
